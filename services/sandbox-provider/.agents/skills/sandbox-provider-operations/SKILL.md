# Sandbox Provider operation procedure

Candidate rc.2 adds scoped file endpoints and a durable file-operation fence. If a transfer is interrupted, inspect the same sandbox/upload; recovery stops the existing runtime before clearing its pending generation. Never clear a pending operation merely because the HTTP caller disappeared. Resume with the original upload and chunk bytes after explicitly starting the stopped environment. Same-guest completion journals do not replace off-host files or backups. Configure workload secrets as runtime-only `WORKLOAD_SECRET_*` variables referenced by `secret_environment`; profiles/DB snapshots contain names only. See `docs/contracts/scoped-files-v1.md`.

Cloud cancellation confirms same-box stop after native kill before terminal status; leader-only kill can leave descendants. Explicit destroy polls exact-ID absence after acknowledgement. If retryable `runtime_transition_pending` leaves registry state `destroying`, replay destroy directly; stop rejects that state. Hosted upload observed about11.5 seconds/MiB, so large bundle staging needs sufficient deadlines. `tests/qa/cloud_transfer_journey.py` qualifies actual hosted file checkpoint/reupload and isolated forensic registry restore with new owned local DBs/loopback Provider. It never starts another Provider against restored bindings and never proves snapshots, coordinated VM recovery, recurring off-host backups or host reboot.

1. Read `services/sandbox-provider/AGENTS.md`, the service `README.md`, and the published API version.
2. Verify virtualization/KVM or supported host backend, BoxLite version, writable disk path, registry connectivity and capacity before starting work.
3. Audit box create/start/run/stop/destroy by `sandbox_id`, actor, correlation ID, timestamp and lifecycle outcome.
4. For restart or recovery, inspect registry and BoxLite disk before reattaching; never recreate a box blindly if the result of a prior operation is ambiguous.
5. On idle stop, confirm run completion and exported artifacts; invoke non-destructive stop, not remove/destroy.
6. Back up and restore registry plus retained disk data consistently; verify persistence after Provider and host restart.
7. Troubleshoot network, resource, profile and startup failures using structured logs without printing secrets or customer files.
8. Before upgrading, pin tested SDK/image versions, verify API compatibility and rollback plan; re-run stop/start/isolation fixture tests afterward.
9. Document tested behavior, failures, unverified assumptions and operational limits; do not claim VM memory or Pi context continuity without tests.

## Implemented candidate operations (2026-11-03)

- Production start: `python -m provider.app`; service directory is the Docker build context. Use pinned `requirements.lock` and the checked-in Dockerfile. Required secret variables are `DATABASE_URL` and `PROVIDER_AUTH_JSON`; approved operator profiles use `PROVIDER_PROFILES_JSON`.
- `/health/live` proves process only. In local mode, `/health/ready` returns503 if DB/KVM/SDK is unavailable; an injected fake returns `runtime:disabled` and can never be counted as verified BoxLite. Cloud mode uses authenticated control connectivity instead of KVM; see its section below.
- Keep `/var/lib/sandbox-provider` in a named persistent volume owned by UID10001. In local mode, `BOX_ROOT` plus the independent PostgreSQL registry require a coordinated off-host backup; follow README's stopped-volume/database restore drill. Cloud disks are external to this volume. Full disk restore and host-reboot validation are incomplete until actually executed.
- Retain `auto_delete=0`, `auto_remove=False`, `detach=True`, standard SDK jailer/seccomp and explicit stop vs destroy. No production auto-fallback, privileged container, Docker socket or arbitrary host mount.
- Query `/v1/sandboxes/{id}/events` with the owning credential for durable safe events. Missing runtime disks become failed, not recreated. `ambiguous_execution` is nonretryable; inspect the stopped environment before manually authorizing a new execution reference.
- Retention configuration denotes archival policy only: append-only audit triggers prevent ordinary UPDATE/DELETE and deduplication/tombstones remain for resource lifetime.
- `GET /metrics` with a `sandbox:read` credential returns owner-scoped Prometheus sandbox/run state gauges; use the same explicit delegation header policy. The automated test verifies unauthenticated denial and cross-owner count isolation. Health remains unauthenticated and carries no resource payloads.
- Set `MAX_CONCURRENT_RUNS` (default4, range1..4) to the qualified host's workload capacity before deployment. This bounds concurrent dispatches per Provider process while reserving PostgreSQL pool slots for API/recovery. Lowering to1 is regression-tested across two queued sandboxes. Keep one production process per BoxLite storage root.
- `python -m scripts.qualify_runtime --session <explicit-lowercase-UUID-hex> --mode lifecycle` is the production-dependency-only operator runtime probe. Use its isolated SDK home in the named volume, never the active API SDK home. A fixed session makes cron replay safe; `prepare` then an independently recorded container replacement then `verify` then `cleanup` can qualify stopped-disk retention. Existing box names/changed identities are refused. Its direct-runtime JSON excludes API/DB/audit/host-restart claims. The eight local safeguard tests use a fake runtime or a missing-KVM negative; only captured real-host results qualify microVMs.
- When Coolify refuses `--group-add`, set optional Docker build argument `KVM_GID` to the host KVM device's positive numeric group ID as a build-time-only variable. The image retains UID/GID10001 and `USER provider` resolves its supplementary group. Default builds add no group; zero/non-numeric values fail. Verify `id` under the exact runtime restrictions and retain narrow `/dev/kvm` mapping. This is device-file permission, not privileged execution or proof of BoxLite compatibility.
- After a failed qualification, `python -m scripts.read_runtime_diagnostic --session <same-session>` reads at most two 8KiB tails from that isolated SDK home's dated `boxlite.log` files. It requires existing session state, refuses directory symlinks, skips file symlinks and redacts configured secrets. It never opens runtime/database state. BoxLite 0.11.0 intentionally hides host causes from Python exceptions; the operator logs retain the actual bubblewrap/KVM diagnostic. Logs do not prove successful VM execution.
- GCC qualification on2026-11-03 reached image/COW-disk setup but failed the bundled bwrap user-namespace preflight: `clone(CLONE_NEWUSER)` errno1, with the SDK detecting AppArmor unprivileged-userns restrictions. Outer default seccomp can also deny namespace/mount calls. Do not load the SDK's generated permissive AppArmor profile, alter host sysctls, add host SYS_ADMIN or disable jailer/security. The README documents a proposed application-only reviewed seccomp/AppArmor correction; it is unapproved and untested. Installing system bubblewrap in an image does not alter the host kernel's loaded profiles or bypass Docker seccomp.
- The current **local-mode** `/health/ready` runtime check is only KVM access/API-version plus SDK-version validation, so it can return200 despite the known bwrap failure. Keep local acceptance blocked. A future bounded startup probe of the SDK-selected bwrap should fail readiness503 on namespace denial/timeout, cache safely and never instantiate VMs from health requests. Do not present local readiness as successful workload capability.

## Hosted Cloud mode

- Explicitly set `SANDBOX_RUNTIME_MODE=cloud`, `BOXLITE_REST_URL`, secret `BOXLITE_API_KEY` and stable `BOXLITE_ACCOUNT_SCOPE`; only use a server-supplied optional `BOXLITE_REST_PATH_PREFIX`. Keep runtime secrets out of build variables and commands. This adapter needs outbound HTTPS/WebSocket access, no local KVM mapping/group or host security changes, and creates no public port/tunnel.
- Keep old immutable profiles authorized for historical reads, and add a new Cloud profile with whole-GiB RAM >=1024MiB, CPU<=16, whole-GiB disk and a suitable fixed operator-owned persistent entrypoint. Retention uses modern `auto_delete=0`, `auto_stop=0`, `auto_resume=False`, plus detached creation. Stop/start polls settled state before reporting completion.
- Migration003 records backend fingerprint and create dispatch authority. Do not reset a creation fence merely because the SDK's first list page lacks a name. An ambiguous create requires exact-name/full-scope operator reconciliation; all retained operations use the returned ID. Do not rebind existing rows to another backend/account or delete account-wide resources. Rotate the key only after confirming the same account; its secret value is excluded from backend identity.
- Cloud `/health/ready` performs an authenticated SDK read and returns503 on refusal/transport failure; it does not depend on GCC KVM. Its200 is not guest execution, resource enforcement or retention proof. Existing local readiness limitations still apply only in local mode.
- The local `qualify_runtime` CLI refuses Cloud mode. Use the lead's deployed HTTP integration prepare/verify/cleanup workflow to qualify real Cloud retention. SDK-loopback and API fake-runtime tests are explicitly mocked, even with real PostgreSQL. Record actual remote IDs privately and destroy only the test resources whose creation authority was recorded.
- Cloud active-command output recovery is blocked: attach fails nonretryable `ambiguous_execution`, stops the same retained environment and never reruns it. Stopped-disk reconnect is a separate test. SDK error-bearing results cannot count as success, and stream-disconnect replay needs independent failure-injection evidence.
- Local persistent volumes contain no hosted guest disks. Back up the Provider registry/audits/configuration and define a separate approved remote data export/restore plan. Reviewed Cloud capabilities disable snapshot/export/import/clone; no full remote guest backup/restore or Cloud physical-host restart proof is claimed. Do not treat normal stop/start or GCC container replacement as those tests.
- GCC Cloud qualification on2026-11-03 passed the actual HTTP prepare→independent Provider/Runner replacement→verify→explicit exact-fixture cleanup journey at deployed04b7dc4. External IDs/backend/disk references and original marker checksum survived; recovery/destruction audits and correlated JSON logs were independently inspected. See `docs/phase1/CLOUD-VALIDATION.md`. Test records now refer to destroyed fixtures: do not recreate/adopt their names or reuse cleanup authority for other boxes. Current guest CPU/RAM/rootfs and denied-route observations are bounded checks, not stress quotas or comprehensive escape proof. Full release remains incomplete for artifact transfer, active-output recovery, off-host/Cloud backup and host-level recovery.
