## Backups and recovery

Use separate scheduled PostgreSQL logical backups for both new database resources, with defined local retention and an operator-configured off-host copy destination. Local backups alone do not survive host/disk loss. Restore backups to isolated resources first and compare migrations, row counts, audit/event identities and pending jobs before cutover. `verify-db-restore.py` performs a disposable local `pg_dump`/`pg_restore` drill against explicitly named test containers, not production.

For **Cloud mode**, back up both databases/audits/configuration and separately define an approved remote guest data export/restore procedure. Observed Cloud capabilities disable snapshot/export/import/clone; full registry-plus-guest recovery remains blocked. Never represent the GCC named volume or same-box stop/start as a Cloud backup. Active-command output attachment also remains incomplete and fails closed; stopped-box replacement recovery is the separately passed journey.

A consistent **local-mode** Provider backup requires a maintenance window: prevent new submissions, drain/cancel active runs truthfully, stop all retained boxes through the API, stop the Provider process, capture its registry database and entire BoxLite named volume as one recovery set, then restart and verify registry-to-runtime identity before resuming Runner. The backup must preserve ownership, permissions and relative SDK disk paths. Keep the SDK and service versions plus image digests with that recovery set. Encrypt and copy it off-host; test restoration to an isolated KVM-capable host. A volume or a registry-only dump is not a recoverable VM backup.

Never automatically recreate a sandbox if a retained disk is missing. Mark it failed, preserve the identity and audit record, and restore its matching recovery set. Rollback uses the prior immutable service commit/image with a database backup compatible with that version; do not drop forward-migrated tables while jobs may still reference them. Both service READMEs describe their migration reversibility and exact recovery commands.

The final verification record states which backup/restore and restart tests actually ran. Host-restart and BoxLite disk-restore qualification remain incomplete until safely executed on authorized hardware.

## Logical state migration when database tools are unavailable

`migration-archive.mjs` and `migration-archive.py` are service-owned-credential operator helpers for the Runner and Provider databases respectively. Prefer native PostgreSQL backups for routine operations. These helpers were used because the application images did not have `pg_dump`; they capture logical row JSON plus sequence state, not schema definitions or VM disks. Apply the same pinned service migrations on the destination first.

Keep source/target quiescent: no queued/active jobs, pending schedules or active runs. Run each helper in its owning application's environment. Default mode exports authenticated encrypted JSON only. Set a private `PHASE1_ARCHIVE_PASSWORD`, or use the documented own-service default token. Never print decrypted rows, export envelopes or password values into public logs. Capture envelopes privately with mode600. An operator can decrypt and re-seal offline to a new target key; do not copy source credentials onto the target.

Restore with `--restore --allow-bootstrap-metadata`, receiving the encrypted envelope through the temporary runtime-only secret `PHASE1_ARCHIVE_ENVELOPE` or stdin. The optional bootstrap flag permits only exact semantic migration matches with differing applied-at timestamps. Destination schemas/columns must match, conflicting rows are rejected, audit triggers remain enabled, and every restored table must match its source digest/count. Nonterminal Runner work is rejected. Provider records with retained runtime identities require a separately verified matching filesystem recovery set and explicit `--allow-retained-runtime-records`; do not use that flag for an empty runtime registry.

PostgreSQL sequence changes are not transactional: keep the target quiescent until successful return and replay after interruption. Successful same-archive replay is idempotent. Verify historical resources/audits through HTTP, replace applications independently, repeat retention checks, then remove temporary envelope variables/tasks and replace containers again to clear their old environments. Remove source resources only after destination verification and a fresh exact project-membership check. Archive manifests/digests can be committed; payloads/keys must remain private. Logical success does not prove guest filesystem preservation or full disaster recovery.
