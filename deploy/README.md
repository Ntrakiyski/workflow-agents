## Backups and recovery

Use separate scheduled PostgreSQL logical backups for both new database resources, with defined local retention and an operator-configured off-host copy destination. Local backups alone do not survive host/disk loss. Restore backups to isolated resources first and compare migrations, row counts, audit/event identities and pending jobs before cutover. `verify-db-restore.py` performs a disposable local `pg_dump`/`pg_restore` drill against explicitly named test containers, not production.

For **Cloud mode**, back up both databases/audits/configuration and separately define an approved remote guest data export/restore procedure. Observed Cloud capabilities disable snapshot/export/import/clone; full registry-plus-guest recovery remains blocked. Never represent the GCC named volume or same-box stop/start as a Cloud backup. Active-command output attachment also remains incomplete and fails closed; stopped-box replacement recovery is the separately passed journey.

A consistent **local-mode** Provider backup requires a maintenance window: prevent new submissions, drain/cancel active runs truthfully, stop all retained boxes through the API, stop the Provider process, capture its registry database and entire BoxLite named volume as one recovery set, then restart and verify registry-to-runtime identity before resuming Runner. The backup must preserve ownership, permissions and relative SDK disk paths. Keep the SDK and service versions plus image digests with that recovery set. Encrypt and copy it off-host; test restoration to an isolated KVM-capable host. A volume or a registry-only dump is not a recoverable VM backup.

Never automatically recreate a sandbox if a retained disk is missing. Mark it failed, preserve the identity and audit record, and restore its matching recovery set. Rollback uses the prior immutable service commit/image with a database backup compatible with that version; do not drop forward-migrated tables while jobs may still reference them. Both service READMEs describe their migration reversibility and exact recovery commands.

The final verification record states which backup/restore and restart tests actually ran. Host-restart and BoxLite disk-restore qualification remain incomplete until safely executed on authorized hardware.

## Logical state migration when database tools are unavailable

`migration-archive.mjs` and `migration-archive.py` are service-owned-credential operator helpers for the Runner and Provider databases respectively. Prefer native PostgreSQL backups for routine operations. These helpers were used because the application images did not have `pg_dump`; they capture logical row JSON plus sequence state, not schema definitions or VM disks. Apply the same pinned service migrations on the destination first.

Keep source/target quiescent: no queued/active jobs, pending schedules or active runs. Run each helper in its owning application's environment. Default mode exports authenticated encrypted JSON only. Set a private `PHASE1_ARCHIVE_PASSWORD`, or use the documented own-service default token. Never print decrypted rows, export envelopes or password values into public logs. Capture envelopes privately with mode600. An operator can decrypt and re-seal offline to a new target key; do not copy source credentials onto the target.

Restore with `--restore --allow-bootstrap-metadata`, receiving the encrypted envelope through the temporary runtime-only secret `PHASE1_ARCHIVE_ENVELOPE` or stdin. The optional bootstrap flag permits only exact semantic migration matches with differing applied-at timestamps. Destination schemas/columns must match, conflicting rows are rejected, audit triggers remain enabled, and every restored table must match its source digest/count. Nonterminal Runner work is rejected. Operational Provider restoration with retained runtime identities requires a separately verified matching guest/filesystem recovery set and explicit `--allow-retained-runtime-records`. Never start a Provider against empty or unverified runtime bindings. The isolated verifier has a separate `--infrastructure-only --forensic-registry-only` mode: it restores those rows into new disposable databases solely to compare hashes/audit IDs/sequences, starts no Provider/Runner/Cloud client and explicitly forbids operational cutover. This mode is forensic database proof, without a guest-disk recovery claim. The verifier bounds and hashes each encrypted envelope against its capture manifest before creating any database, then passes those exact checked bytes through stdin to avoid Linux per-environment-string limits. Missing, stale, oversized or incomplete sets fail before restoration.

PostgreSQL sequence changes are not transactional: keep the target quiescent until successful return and replay after interruption. Successful same-archive replay is idempotent. Verify historical resources/audits through HTTP, replace applications independently, repeat retention checks, then remove temporary envelope variables/tasks and replace containers again to clear their old environments. Remove source resources only after destination verification and a fresh exact project-membership check. Archive manifests/digests can be committed; payloads/keys must remain private. Logical success does not prove guest filesystem preservation or full disaster recovery.

## Minimal application candidate and encrypted off-host checkpoints

The continuation adds three resources in the same project/environment: private `workflow-files` (pinned RustFS plus named volume), private `workflow-application-db`, and the authenticated HTTPS `workflow-application`. IDs are in `application-resources.json`. No Coolify S3 backup destination is used. RustFS stores application objects on GCC; the separate encrypted copies below provide the off-host copy.

`apply-minimal-application.mjs --commit FULL_SHA` prepares configuration without deploying. Supply absolute `COOLIFY_TOKEN_FILE`, `INFRA_CREDENTIAL_FILE`, `APPLICATION_CREDENTIAL_FILE` and `LITELLM_KEY_FILE` paths. The commit must exist locally. The script checks exact project/environment/name, preserves existing actors and updates only the recorded Runner delegate's scopes. Where a token cannot read sensitive environment values, temporary tasks return only existing policies and token SHA256 digests; the helper resolves those against the operator's saved private credentials. An unknown credential fails before mutations. Temporary tasks are removed.

The optional `INCLUDE_QA_ACCOUNT=true` supplies a temporary foreign-owner Basic account and a separate read/destroy-only Provider QA actor for the application service owner. These support explicit recorded fixture verification only; no browser receives Provider credentials. Omit the option, reapply configuration and replace the affected applications after qualification to remove these temporary actors. Never grant the ordinary application credential destroy permission.

Deploy Provider serially with one writer, then Runner and the application at recorded commits. Application readiness uses `node /app/dist/healthcheck.js`; the minimal Node image has no curl. The image also declares the same Docker health probe. A healthy API is insufficient: verify trusted HTTPS, anonymous 401, actual browser submission/list/result, independent file validation, retained audits, safe stopping and replacement persistence separately.

`pull-offhost-backups.mjs` captures encrypted logical Runner/Provider archives and an application checkpoint with all referenced immutable original/result/session files. It verifies authenticated payloads locally, copies ciphertext to a mode-700 directory, writes mode-600 archives plus a sanitized manifest and removes its temporary Coolify tasks. It requires an unchanged healthy finished deployment matching the configured pin before and after each capture; a desired Git pin alone cannot establish the running source. `--infrastructure-only` explicitly excludes the application.

The independent backup host installs `offhost-backup.service` and `offhost-backup.timer` as `workflow-agents-backup.*`. The timer runs daily at 02:40 UTC with up to five minutes jitter. Pin the four operator modules (`deploy/pull-offhost-backups.mjs`, `deploy/migration-archive.mjs`, `deploy/cache-approved-runtime.mjs`, `apps/application/scripts/application-backup.mjs`) and public `deploy/profiles.document.staging.json` inventory under `/opt/workflow-agents-backup/FULL_SHA/` and atomically select that directory with the `current` symlink. This installation remains usable after a development worktree is removed. `/etc/workflow-agents-backup.env` contains paths and the immutable exporter source SHA; separate mode-600 files under `/etc/workflow-agents-backup/` contain only the required recovery keys. Keep a separate protected recovery copy of those keys. The service has a 900-second deadline, read-only filesystem protection and write access only to the backup directory.

Application capture holds SHARE locks while collecting its repeatable row snapshot and immutable object bytes; pending/running requests and unstopped retained sandboxes reject capture. Schedule a quiet window and inspect a nonzero service result rather than treating an incomplete set as success. The bounded format rejects oversized sets without dropping files: 10 MiB per object, 50 MiB total objects, 64 MiB envelope and additional row limits. Larger retained data needs a reviewed streaming format. No automatic backup pruning is installed.

Verify the downloaded set with `verify-offhost-restore.py --infrastructure-only` for infrastructure and `verify-application-restore.mjs` for the application. The latter requires a built matching application, private local test-storage configuration, the archive/recovery-key files and optionally its manifest; it creates new randomly named PostgreSQL/RustFS resources, restores twice and removes only those resources. Both verifiers compare rows, audits and sequences; application restoration also reads back every object/checksum. They start no workload or Cloud client. See the [application checkpoint format](../apps/application/scripts/APPLICATION-BACKUP.md) and [curated evidence](../docs/release/).

These are logical/data checkpoints, not VM disk images. The approved runtime archive is reconstructed from its published asset and verified checksum. Generic file recovery copies required files into a newly recorded sandbox identity; it never binds an old runtime ID to a new disk. Full Cloud snapshots/export/import/clone remain unavailable, active attach remains ambiguous without replay, and shared/vendor host reboot remains unverified.

The puller also retains an immutable mode-600 copy of the already-public approved runtime under `BACKUP_DIRECTORY/runtime/SHA/runtime-bundle.tar.gz`; no private documents or secrets enter that file. New downloads and offline replays verify the pinned checksum. Each session manifest references that cache plus its checksummed `profiles.public.json` inventory, containing secret reference names only. This avoids relying solely on GitHub during recovery. Pass `--runtime-cache /ABSOLUTE/CACHED/runtime-bundle.tar.gz` to the application verifier to reconstruct the archive into its newly created isolated bucket and read back its checksum; ordinary encrypted application objects retain the smaller checkpoint bounds.

`apply-minimal-application.mjs --commit INFRA_SHA --application-commit APP_SHA` can retain the verified infrastructure source while independently pinning an application correction. Omitting the second flag uses the same commit for all three. Both commits must exist locally; configuration readback verifies the corresponding per-service pin. Configuration does not itself deploy either service.
