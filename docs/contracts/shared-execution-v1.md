# Opt-in bounded shared execution — contract candidate rc.3

The owner approved one retained sandbox per authenticated application user and independent concurrent request sessions on 4 November 2026. This requires a generic infrastructure extension; Pi and request-folder semantics stay in the application workload.

Operator-owned sandbox profiles may specify `max_concurrent_runs`, an integer from 1 through 8. Omission preserves capacity one and the existing execution/transfer/cancellation behavior. A shared profile must have a new immutable ID. The first application candidate requests capacity two; a schema upper bound of eight is not a qualification of eight simultaneous executions. Shared execution is Cloud-only until another adapter independently demonstrates equivalent behavior.

Provider claims capacity transactionally under the sandbox lock and retains every active execution identity in its own registry. Runner independently bounds dispatch against the same approved profile capacity and its global/owner limits. `Sandbox.active_run_id` remains a representative active run for existing readers, or null when none remain; it is not an exhaustive listing for a shared profile. Existing HTTP request and response shapes remain unchanged. Clients must not infer that a particular run is the only run in a shared sandbox.

Shared profiles permit scoped file transfers while executions run. File-operation generations, immutable publication, relative-path restrictions, no-follow traversal, size limits and checksums remain enforced. The consuming workload must use separate working directories and immutable shared tools. A transfer fence does not reserve execution capacity; interrupted transfer recovery must not stop sibling executions. Single-run profiles retain their existing busy checks.

Cancellation and attempt deadlines in a shared profile target the exact run's supervisor and descendants, bound to its recorded nonce and runtime identity. Stopping the whole sandbox is forbidden while sibling runs may exist. Unverified termination remains cancelling or ambiguous; missing streams or a native leader exit do not prove completion. A service restart never authorizes fresh execution of uncertain work. Stop and destroy still refuse every active or cancelling run and pending file operation, regardless of which run the representative pointer names.

The application owns preparation and idle shutdown. It uploads and verifies a pinned runtime once, runs the approved preparation workload, then admits independent request sessions. It rechecks all requests, exports and provisioning under its durable workspace lock before stopping the same retained sandbox. Login or new admission and idle stopping serialize using that lock. The initial system prompt and request instructions are snapshotted for each request; they do not establish an OS filesystem boundary.

Release readiness remains false. Mocked tests, real PostgreSQL tests, direct Cloud execution probes and deployed browser journeys must be reported separately. A direct process-group probe alone does not qualify every Provider restart, detached descendant or multitenant resource scenario.
