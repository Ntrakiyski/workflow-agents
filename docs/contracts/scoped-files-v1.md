# Scoped file transfer, v1 candidate extension

Provider `1.0.0-rc.2` adds owner-scoped file endpoints without changing any existing strict `Run`, `Result`, `Sandbox` or Runner request/response shape. `contracts/v1/provider-v1.openapi.json` is authoritative. Both real runtimes require Python3 in the approved guest image for the fixed, reviewed helper. No client chooses an executable, shell, host path, URL or mount.

All paths are relative to `/opt/workflow-transfer` and contain at most16 ordinary components and512 characters. Absolute paths, empty components, traversal, leading-dot components, symlink directories/files, special files and unrelated hardlinks are rejected. Only running sandboxes without active runs or unresolved file operations permit transfer. Authentication, effective owner and allowed sandbox profiles apply on every call. Grant separate `sandbox:file:write` or `sandbox:file:read` permissions explicitly.

1. `POST /v1/sandboxes/{sandbox_id}/files/uploads` with `Idempotency-Key` and `{path,size_bytes,sha256}` reserves an immutable destination and returns `FileUpload`. Maximum file size is256MiB. The database stores metadata/checksums only. Changed canonical request reuse conflicts, and another upload cannot reserve the same path.
2. `PATCH /v1/sandboxes/{sandbox_id}/files/uploads/{upload_id}` with `{offset,data_base64,sha256}` appends at most1MiB decoded bytes. Offsets must be contiguous. Identical previously acknowledged chunks and partial interrupted writes reconcile against the exact bytes; conflicting replay is rejected. JSON bodies are bounded to1500000 bytes.
3. `POST /v1/sandboxes/{sandbox_id}/files/uploads/{upload_id}/complete` with `{}` checks the full size/SHA256 and publishes without overwriting. Lost publication acknowledgements reconcile only this upload's exact staging inode or an identical final file. Successful completion replay returns the same metadata. Original inputs remain immutable through this API.
4. `POST /v1/sandboxes/{sandbox_id}/files/read` with `{path,offset,max_bytes}` returns `{path,offset,data_base64,size_bytes,sha256,eof}`, at most1MiB. The hash describes the entire file. Consumers must verify consistent size/hash across chunks and the independently calculated final checksum before delivery. Only the requested existing guest file is read; no file enumeration or archive extraction is exposed.

Guest helpers use descriptor-relative `O_NOFOLLOW` traversal, regular-file checks, exclusive destination publication and fsync. A persisted pending-operation generation fences workload/lifecycle admission before guest side effects. An interrupted or unconfirmed transfer stops the same retained environment. If stop cannot be confirmed the pending fence remains; operator/startup recovery must stop the same environment before clearing it. Retries reuse the original upload and bytes. A stale completion cannot clear a newer generation. There is no blind replay of workloads and no replacement of sandbox identities.

Cloud preserves these public limits using fixed-helper bounded JSON argv:64 KiB internal writes and32 KiB internal reads. Internal stat tokens never enter public responses. Full hashes bookend each public read; descriptor identity/size/timestamps must remain stable across internal fragments. Consumers still verify the complete exported checksum. Hosted observation found about11.5 seconds/MiB upload; no exact vendor transport limit is claimed.

File upload creation/completion, download start and interruption/recovery produce durable append-only audits with IDs, sizes/checksums and correlation. Paths, bytes and contents are not logged. HTTP auth remains private-service authentication; application authorization must still protect every attachment/result and associate the sandbox with its owned request.

`artifact_output_ref` remains an unsupported external capability and is rejected before execution. These endpoints do not fetch arbitrary URLs or upload directly to object storage. The application/controller owns object storage, export validation and safe sandbox stopping. Guest data export through these endpoints can form part of a separately tested file-level backup, but is not a Cloud snapshot, clone, whole-VM backup or proof of coordinated restore.

## Cloud result completeness

Fresh Cloud workloads execute fixed direct argv through a Python completion wrapper. It drains both child pipes concurrently, retains bounded output, distinguishes truncation and the child exit status, and writes a nonce/checksummed complete-result envelope to `/opt/workflow-transfer/.executions/{run_id}/result.json` before emitting it. Even a silent child produces a complete envelope. Missing, truncated, malformed, mismatched-nonce or checksum-invalid output is nonretryable `ambiguous_execution`, including native exit0 without output.

The journal is same-guest diagnostic/recovery data, not an off-host backup. Active Cloud attachment still fails closed because a complete recovered stream/journal read is not yet independently proven. Provider preserves execution/run identities and stops that same environment without assigning a fresh workload reference. Do not treat rc.2 tests as hosted recovery proof.

## Runtime-only workload secrets

An operator workload profile may specify `secret_environment`, mapping a guest variable name to a Provider process variable named `WORKLOAD_SECRET_*`, for example `{"MODEL_API_KEY":"WORKLOAD_SECRET_MODEL_API_KEY"}`. Profiles and durable run snapshots retain references only. Dispatch resolves values immediately before the runtime call; missing values fail before execution. A name cannot overlap the profile's nonsecret `environment`. Request arguments cannot choose references or secret values. Exact currently configured secret values are redacted from bounded returned stdout/stderr before database persistence; workloads must also prevent secret retention in their files/session output. This mechanism is not a general secret-content detector.

## Evidence boundary

Regression coverage uses real PostgreSQL, actual local guest-helper filesystem operations/subprocesses, and the actual pinned SDK against a loopback HTTP/WebSocket stub carrying fragmented1MiB transfers. Actual hosted evidence is separately recorded in `docs/release/cloud-transfer-journey.json`: a private local Provider against Cloud, exact-fixture cleanup, file checkpoint/reupload and forensic registry restore. These do not prove GCC deployment, host reboot, vendor-host persistence, unrestricted isolation, snapshots or coordinated whole-environment restore. Those gates remain separate in readiness evidence.
