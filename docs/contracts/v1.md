# Phase 1 initial API contract — 1.0.0-rc.1

The authoritative wire schemas are `contracts/v1/runner-v1.openapi.json` and `contracts/v1/provider-v1.openapi.json`. They are generated deterministically by `python3 contracts/build_contracts.py`. This is a reviewed implementation freeze, not a claim that either service or BoxLite passed release gates. Machine release version is `contracts/release.json`.

## Authentication, ownership and errors

Every `/v1` request uses `Authorization: Bearer <opaque-token>`. Configuration maps each token to a stable `actor_id`, allowed profiles, permissions, quotas, resume permission and an effective owner. Never derive identity from request bodies, references or the correlation ID. Tokens must be compared safely and never logged. Private network transport is required; any public endpoint additionally requires TLS. Health endpoints expose no secrets and require no authentication.

The Provider supports explicit delegation for Runner service credentials. Only a token configured with delegation permission may send `X-Owner-ID`, and the selected value must match that delegate's configured owner allowlist. Such tokens must supply the header. Normal clients supplying the header receive 403. The Runner constructs it from the authenticated client's configured owner, never forwards a caller-selected header. The Provider audits `actor_id` (authenticated service), `owner_id` (effective data owner), correlation ID and target separately. To revoke access, remove/rotate credentials and delegation policy in both services. Do not expose a delegate credential to consumers.

Owner mismatch is 404, including on nested runs/events and schedule targets. A known owner requesting a denied profile, destruction or resume receives 403. Quotas return 429. Invalid JSON/header/query is 400; schema or workload arguments is 422; illegal lifecycle transition/busy/idempotency conflict is 409; unavailable dependencies are 503. All errors are the root `{code,message,retryable,correlation_id}` object. Only bounded safe messages/codes are returned; credentials, SQL errors, runtime paths and argument values never appear in errors. Generic codes include `invalid_request`, `unauthorized`, `forbidden`, `not_found`, `idempotency_conflict`, `sandbox_busy`, `invalid_state`, `quota_exceeded`, `dependency_unavailable`, `runtime_unavailable`, `execution_failed`, `deadline_exceeded` and `unsupported_artifact_transfer`. No consumer should treat every 409/503 as permission to repeat a new execution.

Accept/generate `X-Correlation-ID` with the schema's bounded opaque ID format and echo it on responses, logs and audit events. Request bodies are strict objects; reject unknown fields rather than silently accepting shell/image/mount overrides. Body size is at most 64 KiB, canonical workload arguments at most 16 KiB, output at most 32768 characters per stream (also enforce a byte cap operationally), and event page size at most 100. Lower configured limits are permitted and documented; raise them only with explicit operator policy.

## Durable idempotency and recovery

`Idempotency-Key` is mandatory for submission, schedule, resume, sandbox creation and execution. Scope is effective owner + operation + target ID; the same key on a different operation is independent. Fingerprint canonical JSON by recursively sorting object keys and serializing finite JSON values without whitespace. Authenticate and authorize before any replay. The same key/body returns the current resource using the endpoint's original success status; a different body returns 409. Creation plus key/resource mapping and audit must be one transaction. Retain mappings/tombstones for the resource lifetime; audit retention must not erase deduplication records.

Sandbox creation is synchronous at the HTTP boundary: 201 returns the durable current Sandbox, normally `running`. Persist stable runtime name/identity before runtime create, and reconcile that same identity after timeout/crash. A pending/unavailable runtime may return safe retryable 503; retrying the same key must recover the existing operation, never create a second box. Failed/missing disk recovery must not substitute a new empty disk. Create also ensures uniqueness `(owner_id, owner_ref)` for a retained sandbox; profile mismatch is 409. A destroyed tombstone is never silently resurrected; a new environment requires a new owner reference/key.

Execution is asynchronous: 202 returns Run; poll GET Run for real completion and Result. Replays bypass busy checks only after matching the original operation and ownership. Also enforce unique `(owner_id,sandbox_id,execution_ref)`, comparing payload to reject changed reuse. Keep the same execution reference/idempotency key across ambiguous transport errors or service restarts. A new attempt/key is allowed only after the previous run is proven terminal and retry policy permits it. An exit code other than zero is failure, not success. Do not retry unknown side effects as a fresh run.

## Lifecycle

| Resource | Normal transitions | Terminal states |
|---|---|---|
| Job | `scheduled → queued → dispatching → running`; transient proven failure `→ retry_wait → dispatching`; cancellation `→ cancelling → cancelled` | `completed`, `failed`, `cancelled`, `timed_out` |
| Sandbox | `creating → running → stopping → stopped → running`; failure `→ failed`; explicit authorized deletion `→ destroying → destroyed` | `destroyed` (failed requires inspected recovery) |
| Run | `queued → running → completed/failed/timed_out`; cancellation `→ cancelling → cancelled` | `completed`, `failed`, `cancelled`, `timed_out` |
| Schedule | `pending → fired/skipped/failed/cancelled` | all except pending |

Responses can omit intermediate states when an operation completes synchronously. A completed Job/Run remains completed when cancellation arrives late. Cancellation intent is not proof the runtime process stopped; persist cancelling and reconcile before final cancelled/timed_out. Terminal jobs do not revert to queued. Provider stop refuses an active queued/running/cancelling run; start of running and stop of stopped are idempotent. Explicit destroy requires `sandbox:destroy`, `confirm:true`, a reason and no active run. Stop/restart never call destructive remove. No API leaks host disk references or runtime-specific IDs.

`limits.max_duration_seconds` bounds each execution attempt; `max_attempts` bounds proven new workload attempts (transport reconciliation does not consume new attempts). `deadline_at` is an absolute job cutoff and prevents later dispatch; use effective minimum of attempt duration and remaining deadline. Retry only classified transient errors with bounded backoff. Priority follows Graphile semantics (lower number first). The configured global/per-owner concurrency limits apply across worker processes, not just one in-memory semaphore. Provider independently enforces one active run per sandbox in its DB.

`POST /jobs/{id}/resume` requires a terminal owned job with an existing retained sandbox and allowed resume policy. It creates a new job, never mutates the previous result. Body supplies a new Workload/Limits, with optional scheduling fields. The new job implicitly selects `sandbox:{mode:"reuse",sandbox_id:<old>}`. If old job never obtained a sandbox, return 409.

## Delays and schedules

Jobs may specify `run_at`, `deadline_at` and `idle_stop_after_seconds`; all UTC timestamps use RFC3339. A past `run_at` runs as soon as possible. No schedule executes before its due time. `POST /schedules` has exactly one of three actions: `submit_job` with `job`, `stop_sandbox` with `sandbox_id`, or `cancel_job` with `job_id`. The latter implements generic deadlines without a workflow language. References must be authorized at admission and checked at execution.

A stop schedule checks Provider/Runner activity and skips a busy sandbox (status `skipped`, audit reason `sandbox_busy`), preserving disk. It must not blindly retry a stale idle stop after subsequent activity. Automatically generated idle stops capture an activity generation/last completion guard transactionally. A manually scheduled stop requests stop-if-idle at its due time; clients can schedule a replacement after a skip. DELETE pending schedule cancels it; repeated cancellation returns cancelled, already fired/skipped/failed gives 409. Admission and fire/retry/recovery produce durable audit events. GET Schedule is an additive operation for reliable status inspection.

## Events, logs and health

`GET /jobs/{id}/events` and `GET /sandboxes/{id}/events` return `{events:[...],next_cursor:<string|null>}`. Stable exclusive cursors are opaque strings generated from DB monotonic ordering; validate malformed cursors as 400. Events have immutable unique IDs, actor/effective owner, timestamp, target, type, status, correlation and safe bounded detail. Retrying retrieval may redeliver; deduplicate by `event_id`. Preserve operational audit events transactionally with state changes. Never include full workload arguments, output, body payloads or credentials in logs/audit. Resource result output is bounded and owner protected.

Event types are namespaced `job.submitted`, `job.dispatched`, `job.retry`, `job.cancellation_requested`, `job.cancelled`, `job.completed`, `job.failed`, `job.timed_out`, `job.recovered`, `schedule.created`, `schedule.fired`, `schedule.skipped`, `schedule.cancelled`, `schedule.failed`, and Provider `sandbox.created`, `sandbox.started`, `sandbox.stopped`, `sandbox.resumed`, `sandbox.failed`, `sandbox.destroyed`, `sandbox.recovered`, `run.started`, `run.completed`, `run.failed`, `run.cancellation_requested`, `run.cancelled`, `run.timed_out`, `run.recovered`. Additional safe event types are backward compatible. Schedule events must persist in audit storage even when not associated with a job.

JSON logs include timestamp, service, correlation_id, actor_id, owner_id, action, target IDs when available, duration_ms, outcome and safe error classification. `/health/live` tests process only. `/health/ready` tests service-owned DB and queue/runtime; mock or unavailable runtime must be explicitly identified and can never be reported as verified BoxLite. Health shape is `{status,service,version,checks}` with each check `ok|failed|unavailable|disabled`. Separate operational metrics may be added outside the v1 contract.

## Workload and image configuration

`contracts/v1/profiles.schema.json` specifies operator-owned JSON configuration, not a workflow engine. `contracts/v1/profiles.template.json` illustrates fixture write/read workloads. Render the template using a verified OCI digest; unresolved placeholders must fail configuration validation. Never invent an image digest. The image must contain the configured executable (fixture uses Python); BoxLite must execute argv directly, with no shell interpolation. The stock-Python fixture uses existing working directory `/tmp` and its fixed trusted script creates `/tmp/workflow-fixture` before writing; no custom image or preexisting `/workspace` directory is assumed. Only whole argv elements of form `${arg:NAME}` are substituted from validated scalar arguments. Do not interpolate a command string, executable, working directory, environment, mounts or host path from request data. Each profile is bound to allowed sandbox profiles. Adding a future configured image/profile does not change service source or wire schemas.

Sandbox profiles specify pinned image, CPU, RAM, disk cap and network policy. Unsupported SDK security controls must fail closed or block real deployment, not become accepted but unenforced settings. Provider-created writable storage belongs to that runtime identity only; no host mounts, Docker socket or arbitrary shared paths. An allowlist network requires actual supported enforcement; default is denied. Configured client/owner policy authorizes sandbox and workload profile IDs independently.

Phase 1 fixture results may use bounded stdout plus checksummed opaque artifact references. `artifact_output_ref` is an opaque bounded capability understood only by an explicitly configured scoped transfer adapter. If no adapter is configured, nonempty refs are rejected with `unsupported_artifact_transfer` before running. Never fetch caller-supplied URLs or host paths, and never claim unsupported transfers are implemented. Artifact values do not encode business meaning. Artifact transport beyond the configured adapter and production host reboot validation must remain explicit release limitations until tested.

## Compatibility and validation

Pin both service versions/commits as independent releases. RC version does not assert release readiness. Additive optional fields/endpoints/event types are compatible; removing/renaming fields, changing meanings, accepting arbitrary shell, weakening ownership or reinterpreting a known profile ID is breaking. Immutable profile IDs should change version when behavior/image changes. Keep v1 for its documented release support period; major changes require `/v2` and compatibility tests. Responses are strict in this initial contract; future additive fields require updating consumer validation to permit unknown response fields before release.

Run `python3 -m pip install -r contracts/requirements-test.txt` then `python3 contracts/tests/test_contracts.py`. This validates OpenAPI documents, schemas, references, fixture payloads and negative examples. It does not execute services, PostgreSQL or BoxLite. Service and end-to-end tests must validate actual request/response conformance independently.
